# Ревью 2.6.0 / 2.6.1 для следующего патча

Проверены frontend v2.6.0 (`504ea5c7`), v2.6.1 (`3971dce4`), PR #96
(`7f174f3c`) и backend v2.6.0 (`4d5db3ba`) / dev (`40e15ce5`). Отдельного
backend-тега 2.6.1 на момент проверки нет. По решению владельца эти изменения
предназначены для будущей 2.6.2; версии и релизные теги этим ревью не меняются.

## Исправления frontend

- Старые таймеры удаления ключей могли удалить новую генерацию в повторно
  использованном слоте или сократить срок хранения только что сменившегося
  ключа. Теперь таймер относится к конкретному прежнему CryptoKey и запускается
  при его замене; закрытие звонка и удаление отправителя отменяют таймеры.
- Подготовка E2EE личного звонка при ошибке могла перейти к незашифрованному
  звонку. В браузере с поддержкой E2EE такая ошибка теперь останавливает вход.
  Старый режим для браузера без поддержки сохранён.
- Терминальный отзыв ключа/голосовых прав/доступа не запускает автоматический
  повторный вход. Пользователь получает понятную причину завершения.
- Ключи и ACK собираются 10 мс по комнате, затем уходят пакетами до 32 получателей
  только при `ready.e2ee_batch`. На старом сервере используются прежние события.
- `channel.activity` обновляет состояние раз в 250 мс; последнее чужое сообщение
  и курсор собственного сообщения сохраняются отдельно. Пересчёт числовых
  уведомлений ограничен примерно одним запросом в секунду; обычная активность
  не отменяет каждый раз уже выполняющийся запрос и не запускает параллельный
  пересчёт при медленном ответе. Чтение отменяет устаревший ответ. Упоминания остаются отдельным
  счётчиком, обычные непрочитанные сообщения отмечаются точкой в заголовке вкладки.
- PR #96 сохранён вместе с исправлением получателей из 2.6.1: ID трансформации
  привязан к конкретному receiver и стабилен при повторных SDP-переговорах.

## Личное меню, отложенные сообщения и журнал

Диалоги и группы находятся в одном списке. Отдельные кнопки «Диалоги», «Беседы»
и глобальная «Отложенные» удалены. «+ / Новый разговор» открывает выбор людей;
один выбранный человек создаёт ЛС, несколько — беседу. Внутри ЛС «Создать беседу»
уже выбирает собеседника; можно добавить остальных и необязательное название.
Ошибка создания сохраняет выбор.

«Отложенные» под полем ввода показывает только свои pending/failed сообщения
этого чата. Редактирование сохраняет вложения и варианты опроса; вопрос и срок
опроса меняются согласованно. Сохранение текста не переносит близкую отправку
на час, подпись к сообщению с вложением необязательна.

Журнал предлагает имена авторов вместо ввода ID, показывает автора отдельно от
цели и причины. Запоздавшая страница не смешивается с результатами нового фильтра
или сообщества. Имена и причина появляются для новых записей после backend-фикса;
исторические пропуски в БД не восстанавливаются.

Стили действий с сообщениями, заметок и звонка загружаются вместе с их компонентами,
поэтому разделение кода не делает кнопки неактивными до открытия опроса/другой формы.

## Что означает размер 300 kB

Это размер одного минифицированного JS-файла до HTTP-сжатия. Он требует разбора
и выполнения браузером, но не равен сетевой загрузке всего приложения. Сам по
себе такой размер не доказывает проблему. Практическая проблема была в том, что
PR #96 оставлял всего 29 байт от прежнего лимита 300 000, а необязательные функции
попадали в статические зависимости обычного чата.

Замеры одной production-конфигурации Vite, байты; gzip/Brotli вычисляются для
каждого файла стандартным Node zlib. Это оценка сжатого JS, без CSS, изображений,
данных API и динамических загрузок при взаимодействии. Статический граф — entry,
Workspace и все их транзитивные статические импорты, каждый файл учтён один раз.
Небольшая lazy-панель управления личным звонком монтируется после старта; этот
динамический чанк в статический граф не входит и раньше тоже не входил.

| Снимок | Workspace raw | Workspace gzip | Статический граф raw | Граф gzip |
| --- | ---: | ---: | ---: | ---: |
| 2.6.0 | 299 260 | 86 031 | 650 624 | 198 607 |
| PR #96 | 299 971 | 86 284 | 651 404 | 198 870 |
| После ревью | 207 054 | 60 108 | 597 427 | 186 739 |

От PR #96: Workspace −31,0% raw / −30,3% gzip, весь статический граф −8,3% raw /
−6,1% gzip. Сокращение всего графа скромнее, поскольку React и общие модули остаются.
Числа не являются замером скорости реального сервера или слабого телефона.

На требуемое действие перенесены NewsComments, NewsChannelSettings, DirectChat,
выбор собеседников, формы сообщества, журнал и runtime голосового подключения.
Лёгкие проверки браузера, текст ошибок, настройки и кнопки запуска остаются доступны
без загрузки WebRTC. Новые зависимости не добавлены.

`scripts/check-bundle.mjs` проверяет Workspace <250 000, статический граф <620 000
raw / <200 000 gzip и отсутствие необязательных модулей в его транзитивных импортах.
Лимит учитывает весь граф, поэтому перенос кода в общий eager-чанк не скрывает рост.

Повторение: `ANALYZE=true npm run build`; файл `dist/bundle-report.html` показывает
состав. `renderedLength` отдельных модулей в visualizer — не размер минифицированного
чанка, его нельзя складывать с итоговыми raw-байтами.

## Разбор предложений Claude

1. **Batch activity — согласен.** Реализовано. В React Profiler тестовый burst
   200 событий даёт один отложенный коммит Workspace, а не 200. Это проверка числа
   обновлений в jsdom, не измерение FPS реальной истории.
2. **Немедленная первая раздача — согласен, уже есть в PR #96.** Сохранена защита
   ранее записанного одиночного звука: после подтверждённой пустой комнаты новичку
   передаётся новый ключ. ACK ждёт реальной установки в worker; есть ограниченный
   тайм-аут для старых клиентов и пропавших ACK.
3. **Разделение bundle — согласен.** Выполнено с учётом всего статического графа.
   300 kB raw — не 300 kB по сети, поэтому отдельно приведено сжатие.
4. **Batch keys — согласен.** После добавления ACK быстрый burst из 31 ключа и
   31 подтверждения может превысить прежний burst 60. Новый backend транспорт
   проверен настоящим WebSocket: два пакета по 31, затем рабочий ping. Лимит по
   получателям не позволяет превратить пакетирование в неограниченную рассылку.
5. **H(old) → next — отдельный протокол.** Наш вывод: знающий old вычислит всю
   последующую цепочку до добавления новой случайности. Односторонность защищает
   прошлое от новичка, но сама по себе не восстанавливает секретность после
   компрометации. Нужны правила выходов, случайного обновления, эпох, повторов и
   совместимости. Это согласуется с различием sender-key ratchet и обновления
   секретов в [RFC 9420, введение](https://www.rfc-editor.org/rfc/rfc9420.html#section-1)
   и [§16.6](https://www.rfc-editor.org/rfc/rfc9420.html#section-16.6).
   Для этого патча сохранены случайные sender keys и ACK; новый криптопротокол
   не вводится.

Цифры Claude 0,12 мс/кадр и 0,5 мс/wrap отдельно не воспроизводились. На данном
этапе нет оснований менять AES-GCM или добавлять долгоживущий cache shared secrets.
Ограниченное серверное склеивание activity остаётся возможным следующим шагом
для крупных сообществ: текущий backend склеивает очередь медленного клиента,
но не вводит глобальное окно «раз в секунду на канал».

## Проверки

- TypeScript, ESLint и production build с новым бюджетом: pass.
- Vitest: 113 файлов / 486 тестов, pass.
- UI: 56 тестов, затем 6 проверок личного пространства после исправления загрузки
  CSS; pass, включая мобильный экран и клавиатуру.
- Browser performance/reliability: 17/17, pass.
- E2EE Chromium: 11/11, pass, ScriptTransform и insertable streams,
  повторная SDP-переговорка и тишина при неверном/отсутствующем ключе.
- Реальный QA-backend + Chromium: features 2/2 и community 1/1, pass:
  сообщения, группы, файлы, приватность, роли, журнал, отложенная публикация,
  личные/групповые звонки и показ экрана.

Локальная E2EE-фикстура с синтетическим relay RTT 50 мс дала первый расшифрованный
кадр примерно через 31–178 мс и слышимый тон через 134–301 мс. Она использует свой
транспорт обмена ключами и не включает новое 10-мс окно WebSocket-пакетирования.
Это не гарантия production-задержки. Linux race/leak/container проверки выполняет
CI соответствующих PR перед слиянием; локальный Windows не заменяет эти проверки.
